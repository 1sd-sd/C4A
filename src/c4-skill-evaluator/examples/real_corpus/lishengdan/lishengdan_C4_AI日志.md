## 二、我是怎么指挥的（6 轮迭代，含真实指令与真实结果）

### 第 0 轮 — 读懂挑战，先不写代码

**我的指令（大意）**：
> 读完这个文件夹里的 CHALLENGE.md / challenge.json / rubric.json，总结交付物要求和评分维度，然后检查历史提交目录，确认我的提交命名前缀。

**AI 产出**：提炼出交付物模式 `*skill说明*,*.skill,*教学说明*,*demo*,*AI日志*`、五个评分维度、三条 red flag；确认命名前缀 `lishengdan_`。

**我的判断**：这一步决定了选题方向。评分里"被使用次数"权重最高 → 技能必须服务**每个同学每次提交都会遇到**的高频场景，而不是一个炫技但没人用的工具。

### 第 1 轮 — 定选题（我做的决策，AI 提供候选）

**我的指令**：
> 给我 3 个候选技能方向，按"使用频次 × 可确定性 × 上手门槛"排序。

**AI 给了候选**（技能包合规检查器 / 群文件盘点器 / 提交清单生成器）。
**我拍板合并成一个**：`challenge-submission-checker` ——因为"检查是否齐、是否合规、是否干净"正是提交这个动作的**必经步骤**，每个同学每个挑战都要做一次，天然高频。

**我还定了一条硬约束**：零第三方依赖。理由是"可复用"要求陌生人不装任何东西就能跑。

### 第 2 轮 — 出 v1.0

**我的指令**：
> 写 SKILL.md + 确定性检查脚本。要求：支持 challenge.json/yaml 自动探测、--pattern 直给、五维评分、双格式输出（Markdown+JSON）、退出码语义清晰、处理中文路径和 Windows 控制台编码。

**AI 产出**：SKILL.md（169 行）+ `check_deliverables.py` + `references/` 两个文件。

**我发现的问题**：AI 最初照着 CHALLENGE.md 的说法把 `.skill` 当成 tar.gz 打包。
**实际验证**：我解开了资料包里的两个官方示例 `.skill`，文件头是 `PK\x03\x04` —— **是 zip，不是 tar.gz**。
> 这是本次最有价值的一次人工纠错：官方文档自己写错了，如果不实测，交付物格式就错了。

### 第 3 轮 — 构造测试样例，故意"使坏"

**我的指令**：
> 造三个样例包：齐全的（应 PASS）、缺两个交付物的（应 FAIL 并点名缺什么）、脏数据（空壳文件+假密钥+草稿，应 FAIL 且安全维度归零）。再跑 8 项边界测试：yaml 加载、json 自动探测、损坏 zip、空模式、目录不存在、strict 模式、中文路径。

**结果**：8 项边界测试里 **6 项过，2 项暴露真 bug**（见下）。

### 第 4 轮 — 修两个真 bug（v1.0 → v1.1）

这是本次迭代里含金量最高的部分，**两个 bug 都是测试暴露出来的，不是我或 AI 凭空想到的**：

| Bug | 现象 | 根因 | 修复 |
|---|---|---|---|
| ① 草稿文件冒充交付物 | `~$lishengdan_C4_skill说明.docx`（Office 锁文件）命中了 `*skill说明*`，齐全度被刷成假 80% | 交付物匹配发生在垃圾文件过滤之前 | 先剔除 `_*`、`~$*`、`*.bak` 再匹配 |
| ② 分数重复加权 | 同一个 `.skill` 同时计入 `content` 和 `packaging` 两个维度 | "内容质量"取平均时没排除非文本文件 | `content` 只在 `.md/.txt` 上取平均 |

**我的指令**：
> 这两个结果不合理：齐全的包只有 83 分内容分，脏数据的齐全度虚高。逐行排查评分逻辑，找到根因再改，改完跑回归。

修复后三个样例的分数从 `93.8 / 75.5 / 45.0` 变为 `91.8 / 69.5 / 36.3`，且都能解释清楚每一分怎么来的。

### 第 5 轮 — 处理一个"设计层面的假警报"

**现象**：用技能检查"包含它自己源码的提交文件夹"时，把 `examples/` 里**故意**放的假密钥和空壳文件当成真问题报出来（T8 失败）。

**我的决策**：这不是 bug，是真实使用中一定会遇到的场景（提交文件夹里带源码和自测样例很正常）。
**方案**：给脚本加 `--exclude` 参数，并把测试样例移进技能包内成为 `examples/` 自测套件 + `run_selftest.py`。
> 这一轮的收获：好的工具要为自己的测试数据负责，否则测试数据会污染真实检查。

### 第 6 轮 — 打包、自证、出 demo

1. **打包**：zip 结构、顶层目录 = 技能名，产出 `lishengdan_C4_challenge-submission-checker.skill`（24 KB，18 个条目）。
2. **可复用性实测**：把 `.skill` 解压到**全新空目录** `D:/.cogseed/tools/probe/`，跑自测套件 → 3 用例全过。证明零配置可用。
3. **吃自己的狗粮**：用本技能检查它自己的 `.skill` 包 → 包结构 **100/100**。
4. **demo 出图**：要求截图必须是**真实运行输出**，不许手绘示意。AI 最初给的对齐是乱的，我指定用 SimHei（实测半角=全角=等宽），最终 5 张图全部由真实 stdout 渲染。
5. 顺手加了 `--title` 参数，消除报告里的"(未命名)"。

### 第 7 轮 — 用它检查它自己的提交包，又抓出一个误报（v1.1 → v1.2）

把本技能指向 `C4技能分享/` 这个真实提交文件夹，结果出现一条荒谬的警告：

> `lishengdan_C4_skill说明.md：含占位符文本：TODO, 占位, 待补充`

**根因**：这份文档在**介绍**占位符检查时引用了 "TODO 待补充" 这些词——v1.1 只做子串匹配，
于是"讨论占位符的文档"被当成"含有占位符的文档"。

**修复（启发式）**：只有当占位词出现在**行首**（剥掉 Markdown 标记后，如真实的 "TODO 待补充"、"待补充"）才判违规；
出现在句子中间的引用不算。这是本次迭代里第三次"工具吃自己的狗粮发现问题"。

**修复后本提交包自检**：`96.7 / 100，PASS，无阻断项、无建议项`（报告见 `lishengdan_C4_自检报告.md`）。

> 三次狗粮测试各自抓出一类问题：v1.0 抓出打包格式、v1.1 抓出评分缺陷、v1.2 抓出误报。
> "用自己的工具检查自己的交付物" 应该成为固定动作。

## 四、有效 / 无效的提示词（对比）

**无效**：
> "帮我写一个检查提交文件的脚本。"
> → 没有定义输入输出和"合格"的标准，AI 只能猜，产出没法验收。

**有效**：
> "写一个确定性检查脚本，输入一个提交文件夹和一条交付物通配模式，输出 Markdown+JSON 双格式报告和 0–100 分。评分维度和权重我定：齐全度 35 / 内容 25 / 包完整 20 / 卫生 10 / 安全 10。零第三方依赖，退出码 0/1/2 分别表示通过/未通过/用法错误。"

差别在于：**我把验收标准写进了提示词**，AI 的产出直接可以被测试判定对错。

**最有效的一类指令**是把"不合理的结果"直接丢回去：
> "齐全的提交只有 83 分内容分，这说不通。逐行排查评分逻辑。"
> → 让 AI 从"写代码"切换到"调试"，且必须给出根因而不是补丁。

## 六、复盘与经验总结（给下次的自己）

1. **先验证权威材料的说法再照做**。CHALLENGE.md 说 `.skill` 是 tar.gz，实测是 zip。30 秒的解包测试避免了一次格式错误的交付。
2. **测试样例要先"使坏"**。三个样例里两个是故意做坏的，正是它们抓出了两个真 bug。全部用"正确数据"测试等于没测。
3. **把验收标准写进提示词**，而不是写在对产出的事后抱怨里。
4. **对"不合理的感觉"要保持敏感**。两个 bug 我都是先觉得分数不对，再让 AI 排查——如果只看"脚本跑通了没有"，这两个 bug 会一直留在交付物里。
5. **工具要为自己的测试数据负责**，否则自测样例会污染真实检查结果。
